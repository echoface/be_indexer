segmentindex 索引实现逻辑

1. 五分钟总览

一句话：segmentindex 是一个面向查询优化的 DNF 倒排索引。

它把每个文档中的每个 Conjunction 编译成一个独立、不可变的“组”。 查询时先用组级倒排和预计算结构快速排除不可能的组，再对少数候选组做精确布尔判断，最后合并 DocID。

它解决什么问题

  • 一个文档可能有多个条件组合，多个组合之间是 OR。
  • 同一个字段内多个查询值是 OR，不同字段之间是 AND。
  • 排除条件不能和包含条件混在一个普通倒排里直接求交。
  • 查询需要高性能，构建成本可以放到离线阶段。

它为什么快

  • 组和 DocID 都映射到稠密 slot，倒排可以使用紧凑 bitmap。
  • 单 DocID 组走专用快路径，避免创建大量临时 bitmap。
  • 查询值只规范化一次，查询临时对象通过 sync.Pool 复用。
  • 单位区间走点索引，宽区间走带 maxRight 的区间树。
最重要的概念 Document 是业务文档；Conjunction 是一个 AND 条件组合； Group/Segment 是索引内部对该组合的编译结果。一个 Document 的多个 Conjunction 最后要做结果并集。

2. DNF 与分组

DNF 是“析取范式”的简称，可以理解成若干个 AND 条件组之间做 OR。 segmentindex 不把多个 Conjunction 混成一个大倒排，而是给每个 Conjunction 建一个独立 group。 这样可以保证一个 group 内部的字段约束不会跨组串味。

布尔语义拆开看

层级 关系 例子
同一个字段的多个值 OR city In ["bj", "sh"]
同一个 Conjunction 的多个字段 AND city=北京 AND age=30
同一个 Document 的多个 Conjunction OR C1 OR C2 OR C3
包含与排除 先候选，再减去命中排除 include hit - exclude hit
容易误解的地方 同一个 Document 可以有多个 Conjunction。每个 Conjunction 都独立编译成 group， 不能因为它们属于同一个 DocID 就提前合并，否则可能把“只要 C2 命中”误判成“整个 C1、C2 都必须命中”。

3. 构建流程

构建阶段把结构化的 Document 变成两部分：倒排 term posting，以及无法表达成 exact term 的 range predicate。 每个 group 完成后会 seal 成不可变的 storage.Segment。

3.1 Exact term 的编码

include 和 exclude 不能只靠 DocID list 区分，因此 term value 会带一个私有前缀。 这个前缀只存在于索引内部，业务查询值不需要手工添加。 

include value       -> "\x01" + value
exclude value       -> "\x02" + value
exclude-only fallback -> "\x03"

fieldShape 记录某个字段是否使用过 include、是否使用过 exclude。 它既服务于查询时的 wildcard fallback，也是压缩时 group 是否可以合并的重要依据。

3.2 半开区间

所有数字 range predicate 最终都写成 [left, right)，也就是包含左边界、不包含右边界。 这样可以统一 GT、LT、Between 的语义，也能避免同一个值在边界处重复命中。

原始表达式内部区间含义
GT v[v+1, MaxInt64)严格大于 v
LT v[MinInt64, v)严格小于 v
Between l,h[l, h)包含 l，不包含 h
Between l,l[l, l+1)等价于精确值 l
边界规则 浮点数会被拒绝，防止截断成整数后产生静默错误。区间只接受整数或整数字符串。

4. 存储结构

storage.Segment 负责倒排数据本体，groupMeta 负责 Segment 本身不容易表达的语义元数据。 两者合起来才是一个完整的 group。

4.1 为什么要有 queryIndex

如果只把数据交给普通倒排执行器，每个查询都要重新做很多临时对象分配、字符串比较和 bitmap 运算。 queryIndex 在 newIndex 阶段把常见查询模式提前算好。

  • 每个 group 映射到连续的 [slotStart, slotEnd)，slot 再映射回 group 和 doc。
  • term posting 直接记录 slot，而不是查询时反复从 DocID 重新映射。
  • 单 DocID group 的 posting 内联一个 slot，常见情况下不额外分配 slice 或 bitmap。
  • 数字 term 同时保留字符串 map 和 int64 map，数字查询避免反复格式化。

4.2 queryPosting 的小优化

type queryPosting struct {
    single uint64
    slots  []uint64
    count  int
}

当一个 term 只命中一个 slot 时，直接保存 single； 只有命中多个 slot 才分配 slots。这是针对单文档 group 大量存在的常见场景做的微优化。

5. 查询执行

推荐使用 RetrieveAssignments 或 RetrieveAssignmentsInto。 它们是完整的 DNF 查询入口，能够处理 exact term 和 GT/LT/Between。 Retrieve(planner.Query) 主要用于 exact-term 兼容路径，不适合包含 range 的完整文档语义。

5.1 查询语义

  1. 字段内取并集：city In ["bj", "sh"] 的两个值只要命中一个即可。
  2. 字段间取交集：city 和 age 都要满足。
  3. 包含条件：include 命中是候选条件。
  4. 排除条件：exclude 命中会从候选中减掉。
  5. 未查询字段：查询里没传的字段不会限制当前 group。
  6. 多个 Conjunction：每个 group 的结果最后取并集并按 DocID 去重。

5.2 Include / Exclude 示例

Conjunction:
  city In ["bj", "sh"]
  age  Between [20, 30)
  city NotIn ["sh"]

等价于：
  (city in {bj, sh})
  AND (age in [20, 30))
  AND (city not in {sh})

执行时并不是把三个 posting 直接 AND。include 和 exclude 分开收集， 最终用“包含候选集合 - 排除命中集合”的方式判断。

5.3 为什么要区分单 DocID group 和多 DocID group

一个 group 如果只包含一个 DocID，那么 group 命中就等于 DocID 命中，可以直接返回。 如果一个 group 包含多个 DocID，就必须在 group 内部继续判断每个 slot， 否则 A 文档的 term 命中可能把同一 group 中的 B 文档也带出来。

5.4 Group Query：group 级筛选与 slot 级精判

Group Query 不是简单地把所有 DocID posting 直接求交。为了避免多个文档共处于一个 merged group 时发生“串组误匹配”，查询分成 group 级和 slot 级两层。

Group 级：先缩小候选 group

对每个查询字段，把该字段所有查询值的 group posting 取并集，再把不同字段的 命中集合取交集。某个字段没有被文档限制时，该字段不会淘汰这个 group。 

fieldHits(field, values)
  = union(groupPosting[value] for value in values)

candidates
  = allGroups
  candidates ∩= fieldHits(field1)
  candidates ∩= fieldHits(field2)
  ...

Slot 级：再判断 group 内每个文档

多 DocID group 只能先保留候选，不能直接把 group 中所有文档都返回。 matchGroupSlots 在连续的 slot 区间上逐文档判断 include、exclude 和 range。 

slots(group)
  = [groupSlotStart[group], groupSlotEnd[group])

resultSlots
  = slots(group)
  resultSlots ∩= includeHits(field1)
  resultSlots ∩= includeHits(field2)
  resultSlots -= excludeHits

例如 M1 包含 DocID 102, 103, 105, 108, 109, 110。如果查询只命中 105, 108，group 级阶段可以保留 M1，但 slot 级阶段必须继续排除 102, 103, 109, 110，不能把 M1 的所有成员一起返回。

规则Group 级处理Slot 级处理
include exact term / range 作为候选条件；多文档 group 可能被宽泛地保留 逐 slot 精确确认是否命中
exclude exact term / range 只对单 DocID group 安全地直接淘汰 多 DocID group 必须逐 slot 减掉 exclude 命中
查询未传的字段 不淘汰当前 group 不淘汰当前 slot
多个查询值 字段内先 union 同一 slot 命中任意一个值即可

5.5 多选值在 Group Query 中的处理

多选值在同一个字段内部是 OR，在不同字段之间仍然是 AND。构建时每个值都会写入独立 term；查询时这些 term 的 posting 先做并集，再参与 group/slot 过滤。 

Document:
  city In {bj, gz}

Query:
  city In {bj, gz}

字段内：
  city=bj 的 posting
  ∪ city=gz 的 posting

字段间：
  city 的候选
  ∩ device 的候选
  ∩ age 的候选
注意： 多选值不会自动展开成多个 Conjunction。它仍然属于同一个 group，因此不会破坏 DNF 边界；groupSignature 也不关心具体 term 值，只关心表达 shape 和 range 边界。

5.6 单 DocID group 快路径

如果索引中所有 group 都只包含一个 DocID，查询会尝试选择一个最 selective 的 required exact-term 字段作为入口，直接从 group posting 生成 DocID，不创建 group bitmap 或中间候选集合。

  1. 要求当前索引是 allSingle。
  2. 选择命中 group 数最少的 required exact-term 字段。
  3. 对该 posting 中的每个 group 调用 groupMatches。
  4. 最后统一过滤 tombstone，并对接收的 dst 做排序和去重。

如果存在宽泛 term、range-only 条件或索引中包含多 DocID group，则回退到 matchGroups → matchGroupSlots 的 bitmap 路径。

5.7 结果缓冲区

RetrieveAssignmentsInto 会把返回的 slice 复用起来。 对在线高频查询，这能显著减少每次查询的 make([]DocID) 分配。

6.2 步骤 A：构建 Document / Conjunction

每条数据都编译成一个 Document，内部放一个 Conjunction。示意代码如下：

type demoRow struct {
    ID             int64
    Cities         []string // 多选城市，字段内 OR
    Devices        []string // 多选设备，字段内 OR
    ExcludeDevices []string // exclude-only 设备
    Age            int64
}

func demoValues(values []string) be.Values {
    return be.NewStrValues(values[0], values[1:]...)
}

func demoDocument(row demoRow) *be.Document {
    conj := be.NewConjunction().
        In("city", demoValues(row.Cities)).
        Between("age", row.Age, row.Age+1)

    if len(row.Devices) > 0 {
        conj.In("device", demoValues(row.Devices))
    }
    if len(row.ExcludeDevices) > 0 {
        conj.NotIn("device", demoValues(row.ExcludeDevices))
    }

    return be.NewDocument(be.DocID(row.ID)).AddConjunction(conj)
}

demoValues(row.Cities) 会把多个值编译进同一个 Conjunction 的同一个字段， 不会为每个 city 值创建新的 Conjunction。

6.6 步骤 E：查询如何匹配

查询条件故意让 city 使用多选值：

city In {bj, gz}       // 字段内 OR
device = "ios"
age = 25

逐字段看集合

city = {bj, gz}
  = {101, 102, 104, 106, 108, 110}   // city=bj
  ∪ {102, 105}                        // city=gz
  -> {101, 102, 104, 105, 106, 108, 110}

device = ios
  -> {101, 103, 104, 105, 107, 108, 109, 110}
     // 107 的 device 是 exclude-only，查询 ios 不会被排除

age = 25
  -> {102, 103, 105, 108, 109, 110}

三者交集
  -> {105, 108, 110}
关键结论 查询不是简单地“把三个 posting 求交”。它先把字段局部候选求并，再在同一个 Conjunction/Group 内求交， 最后把 exclude 命中减掉，并把多个 Group 的 DocID 合并去重。

6.7 再验证一个 Exclude 场景

query:
  city = "sh"
  device = "android"
  age = 35

G7 的文档条件：
  city=sh
  device NOT IN {android, tablet}
  age∈[35,36)

G7 在 city 和 age 上是候选，但 query 的 device=android 命中 G7 的 exclude posting， 所以 G7 被减掉。反过来，如果查询 device=ios，G7 可以通过 exclude-only wildcard 规则保留。

7. 数字区间索引

range 查询不是普通的 exact term posting，因为一个区间可能覆盖很多值。 queryRangeIndex 采用两种结构：

单位区间：点索引

形如 [x, x+1) 的区间其实就是精确值 x。

points[x] -> roaring bitmap(slot IDs)

查询 x 时直接 map 查找，成本近似 O(1)。

宽区间：区间树

形如 [l, r) 的区间保存在静态区间树中。

node.maxRight = max(node.entries.right)

query x:
  prune if node.maxRight <= x
       or node.leftBound > x

用 maxRight 剪枝，避免扫描所有小于 x 的区间。

8. 增量更新、快照与压缩

如果需要在线写入，底层的 Store 不会直接修改已经发布的 Index。 它把变更累积成 delta，通过 tombstone 处理删除和更新，再用不可变快照保证查询稳定。

7.1 Tombstone 如何判断版本

tombstone.dead(id, addSeq) == true
when tombstoneSeq > addSeq

所以一次删除只杀死比删除序列更早的版本。之后重新 Add 的同 ID 文档拥有更大的 add sequence，仍然可见。

7.2 为什么压缩不能随意合并 group

groupSignature 包含每个字段的 include/exclude shape，以及 range predicate 的边界和方向。 exact term 的具体值不在签名里，因为它们可以通过 posting 合并。 

same signature + disjoint doc IDs  -> 可以合并
same signature + shared doc ID     -> 必须保持分开

共享 DocID 可能表示同一个文档的多个 Conjunction，也可能是同一个文档的不同版本。 随意合并会破坏 DNF 边界或 tombstone 的版本判断。

并发模型 已发布 Index 是不可变的。查询临时 bitmap 放在 query scratch 中，并通过 sync.Pool 复用； Store 通过不可变 view 发布状态，快照 pin 住旧 view，压缩不会影响正在进行的查询。

9. API 示例

下面示例展示最常用的离线构建和查询方式。完整 benchmark 代码可参考 benchmark/retrive_test.go。

package main

import (
    "fmt"

    be "github.com/echoface/be_indexer"
    "github.com/echoface/be_indexer/segmentindex"
)

func main() {
    builder := segmentindex.NewBuilder()

    doc := be.NewDocument(be.DocID(1001)).AddConjunction(
        be.NewConjunction().
            In("city", be.NewStrValues("bj")).
            In("device", be.NewStrValues("ios")).
            Between("age", 20, 30),
    )

    if err := builder.AddDocument(doc); err != nil {
        panic(err)
    }

    index, err := builder.Seal()
    if err != nil {
        panic(err)
    }

    assignments := be.Assignments{
        "city":   be.NewStrValues("bj"),
        "device": be.NewStrValues("ios"),
        "age":    be.NewInt64Values(25),
    }

    var dst []be.DocID
    dst, err = index.RetrieveAssignmentsInto(dst, assignments)
    if err != nil {
        panic(err)
    }
    fmt.Println(dst)
}

8.1 在线 Store 的最小写法

store := segmentindex.NewStore(segmentindex.StoreOptions{})
if err := store.AddDocument(doc); err != nil {
    return err
}
if err := store.Flush(); err != nil {
    return err
}

snapshot := store.Snapshot()
defer snapshot.Close()
ids, err := snapshot.RetrieveAssignments(assignments)

注：具体方法名以当前源码为准；核心模型是 Store -> Delta -> Snapshot，查询端读取的是固定快照。

10. 常见误区

  • 误区一：“segment 就是一个大倒排表”。
    实际上这里的 segment 更像一个 Conjunction 编译单元；一个 Document 可以产生多个 segment。
  • 误区二：“include 和 exclude 可以直接对 DocID 求 AND”。
    exclude 应当从候选中减掉，并且 group 级排除只对单 DocID group 直接安全。
  • 误区三：“range 可以用字符串 exact term 表示”。
    range 需要独立的半开区间结构，尤其是连续整数范围不能展开成海量 term。
  • 误区四：“同 signature 的 group 都能合并”。
    还必须保证 DocID 集合不相交，否则会破坏 DNF 或版本边界。
  • 误区五：“查询时再做一次字符串转换没关系”。
    高频查询应尽量使用 RetrieveAssignmentsInto、数字 int64 路径和可复用结果缓冲区。

12. 理论依据与多选值设计

这一章回答三个常见问题：segmentindex 是否有论文依据、当前是否支持多选值、 万级多选值是否应该换索引类型，以及 ahoholder 是否合适。

12.1 KGroups 与 segmentindex 的关系

be_indexer_kgroups 更接近论文中的 Boolean Expression Indexing / K-Groups 路线： 把布尔规则按条件组合编译成 posting，再按规则组进行匹配。 仓库 README 也明确说明，这套算法描述来源于 Boolean expression indexing。

segmentindex 不是另一篇论文算法的逐行复现，而是针对当前项目的查询优先目标重新组织的工程实现。 它保留了同一个问题模型：给定大量 DNF 规则，输入一个 assignment，找出满足条件的文档； 但物理执行层改成了“不可变倒排段 + 稠密 slot + bitmap 集合运算 + 区间索引 + 增量快照”。

12.2 segmentindex 的理论依据

技术在 segmentindex 中的作用理论来源
DNF / Boolean Expression Indexing 把 Document 拆成 Conjunction group，保持 AND/OR 边界 Boolean expression indexing、规则索引
Inverted Index / Posting List term 到 DocID 或 slot 的映射 倒排索引基础结构
Bitmap Set Algebra 候选求交、求并、排除、去重 Roaring bitmap / bitset 运算
Interval Stabbing Query 查询数值是否落入 [left, right) segment tree / interval tree
LSM / Delta / Snapshot 增量写入、不可变快照、后台 Compaction LSM-tree、MVCC、immutable view
更准确的说法 segmentindex 的理论依据不是一个单独命名的“segmentindex 算法”，而是把 DNF 规则索引、倒排索引、bitmap、区间查询和 LSM 增量思想组合成一个查询优先的实现。 如果需要引用论文，可以引用 Boolean Expression Indexing 作为问题和 K-Groups 的理论背景，但不要把 segmentindex 描述成论文算法的直接复刻。

12.3 当前是否支持多选值

支持。这里的“多选值”有两个方向，两者都由 be.Values 表达：

场景例子当前语义
文档侧多值 In("tag", NewStrValues("a", "b", "c")) 一个字段的多个值是 OR，任一值命中即可
查询侧多值 "tag": NewStrValues("a", "b", "c") 多个 query value 的 posting 做 union
范围值 Between("age", 20, 30) 独立的 range predicate，不展开成枚举 term 
// 文档：tag 可以是多个值
doc := be.NewDocument(id).AddConjunction(
    be.NewConjunction().In("tag", be.NewStrValues("a", "b", "c")),
)

// 查询：query 也可以传多个值，结果取 OR
assignments := be.Assignments{
    "tag": be.NewStrValues("a", "b", "c", "d"),
}

当前实现会为每个 exact value 建立 term posting；查询时把多个 value 的 posting 合并。 因此“万级多选值”在语义上是支持的，但会带来 term 数量、查询规范化、posting 合并和去重成本。

12.4 多选值达到万级时怎么选

工作负载推荐结构原因
精确 tag 集合，tag In [10k values] 继续使用 inverted posting，但增加 value dictionary / int64 ID 避免每个查询值都走字符串格式化和字符串 map；用批量 Roaring union
查询值很多，且结果集合也很大 值 ID 化 + Roaring bitmap，或 bit-sliced bitmap 减少 per-value 分配，利用 bitmap 的 union/intersection/difference
低基数字段，查询经常要求大范围枚举 直接 bitmap matrix / 列式 bitset 所有值共享同一 DocID universe，集合运算更稳定
文本中包含任意关键词 ahoholder 或其他多模式匹配结构 这是 substring/keyword matching，不是 exact set membership
连续数字区间 range index 不要把区间展开成上万个 exact term
是否需要新建索引类型 如果“多选值”仍然是精确的 In / NotIn，不需要马上引入新的语义索引； 优先在现有 segmentindex 上增加 dictionary-backed multi-value fast path。 只有当工作负载变成“文本包含关键词”或“大量值的集合矩阵”时，才需要单独的 holder/index 类型。

12.5 ahoholder 是否合适

ahoholder 基于 Aho-Corasick 自动机，适合“一段文本是否包含多个关键词中的任意一个”。 它不是为精确多选集合匹配设计的。

需求ahoholder 是否合适说明
tag In ["a", "b", "c"] 不合适 这是精确 term membership，应使用 inverted posting
content contains ["比特币", "以太坊"] 合适 这是多模式子串/关键词匹配
万级关键词扫描长文本 可能合适 适合一次扫描文本匹配多个 pattern，但要评估字典内存、重叠匹配和输出量
数值范围 age Between [20, 30] 不合适 应使用 range index

当前 ACEntriesHolder 只接受 EQ 语义，并通过 MultiPatternSearch 在拼接后的查询内容中找关键词。 如果把它用于 tag 的万级 exact 多选，可能出现分隔符、子串和重叠 pattern 语义问题，性能也不如 hash map + inverted posting 直接。

12.6 推荐决策

  1. 精确多选：保留 segmentindex / default holder，增加值字典和批量 bitmap union。
  2. 文本关键词：使用 ahoholder，并明确“包含”而不是“等于”的语义。
  3. 范围：保留 range index，不把连续范围物化为大量 exact term。
  4. 混合字段：把 exact tag、文本关键词、数值范围拆成不同字段或不同 holder，避免一个索引承担多种物理语义。
一句话结论 segmentindex 的理论根基是 DNF 布尔索引和经典索引结构的组合； 多选值已经被支持，万级多选首先要优化 value ID 和 bitmap 合并，而不是直接换成 Aho-Corasick。

相关源码： README.md、 Boolean expression indexing 设计图、 ahoholder 实现、 segmentindex/query.go。

13. 最终心智模型

把 segmentindex 想成一台“离线编译器 + 在线过滤器”：

  1. 离线编译：把 Document 拆成 DNF group，把条件编码成 term、range、shape、sequence。
  2. 预计算：把 group 和 DocID 映射成 slot，把 term 和 range 变成可快速定位的 posting。
  3. 在线过滤：先把不可能的 group 剪掉，再只对少量候选做精确判断。
  4. 结果收敛：处理 tombstone，合并多个 group 的 DocID，排序去重，复用结果缓冲区。
记住这条线 Document → Conjunction → Group/Segment → queryIndex → bitmap/slot → DocID
