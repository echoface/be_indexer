Why another index

规则引擎的瓶颈，
通常不是“查词”，而是“证明不命中”。

当规则是带 AND、OR、否定和数值区间的布尔表达式时，普通倒排索引只能回答“这个词出现在哪里”，却无法高效回答“这个 Document 是否整体成立”。

01 / 组合爆炸

一条规则是多个字段的 AND

逐条正向求值意味着每条规则都要扫一遍 Assignment。规则从十万涨到千万，查询延迟也随之线性上涨。

02 / 更新成本

重建一次，停服一次

规则每天都在增删改。没有不可变快照与增量层，构建、发布、回滚就会变成停机窗口和文件锁。

03 / 语义边界

否定、通配与区间无处安放

Exclude 不是“查不到”，K=0 的通配也不是“空条件”。这些语义一旦建模错，线上就是静默漏召回。

The design answer

六个决定，
把复杂度留在离线。

在线路径只做三件事：把 Assignment 编码成游标，让游标竞速，把命中的 DocID 交给 collector。

完整架构 →
01

K 直接编码进 EntryID

Conjunction 的 Include 数占 EntryID 高 8 位。相同 K 的条目天然相邻，查询时动态读取，不需要物理 K 分桶。

02

单次多路归并

所有字段、所有 segment、wildcard 的游标进入同一张排序表。第 max(K,1) 个头部就是 pivot，一次推进一批。

03

mmap 零拷贝

Segment 按 8 字节对齐、小端序落盘。对齐的小端主机直接把 posting 借成 []EntryID，cold start 只映射，不复制。

04

可插拔索引容器

同一个 FlatPostingList，之上可以是 FlatDict、MPH、FST、AC 自动机或区间树。索引类型与值编码是两个正交轴。

05

full + delta 快照

全量代 + 累计增量层，通过不可变 manifest 与原子 CURRENT 切换。热更新时旧 mmap 等最后一个查询结束再回收。

分数不塞进 Segment。独立不可变分数表提供块上界，在布尔 pivot 之后剪掉整段不可能进入 Top N 的区间。

    Quick start

    六个调用，
    从规则到结果。

    构建、加载、查询都在同一个包里。生产环境再切到 full + delta + manifest + Holder。

    i

    最小可运行示例：单 Segment 适合验证语义与容器选型；只要规则会更新，就应直接使用 full + delta 链路。

    gomain.go
    fields := be_indexer.Schema{
    "age":  {IndexType: "ext_range", Encoder: "ext_range"},
    "city": {IndexType: "default"},
}

doc := be_indexer.NewDocument(1).AddConjunction(
    be_indexer.NewConjunction().
        Between("age", 18, 25).
        In("city", be_indexer.NewStrValues("beijing")),
)

var buf bytes.Buffer
_ = be_indexer.BuildSegment(&buf, fields,
    []*be_indexer.Document{doc}, be_indexer.BuildSegmentOptions{})

reader, _ := be_indexer.NewSegmentReader(buf.Bytes())
engine, _ := be_indexer.NewEngine(
    fields, []*be_indexer.SegmentReader{reader})

res, _ := engine.Retrieve(be_indexer.Assignments{
    "age": []int{20}, "city": []string{"beijing"},
}) // → DocID 1
    “低分配是性能手段，不是削弱功能的约束。项目首先保证布尔规则语义、数据完整性和线上可用性，再通过 mmap zero-copy、游标归并、外排和对象复用降低延迟与内存开销。” — 仓库 README 的设计取舍
