01 · 两阶段检索：先布尔，再排序

检索被拆成两个问题：哪些 Document 满足查询输入？在满足的 Document 中，哪些分数最高的 N 个？两者共享同一次布尔遍历，但正确性依据完全不同。

figure 12two proofs, one cursor advance
i

为什么 pivot 之后的分数上界是安全的？上界只用于“跳过不可能胜出的区间”，从不把不匹配的 Document 变成匹配。所有实际结果仍经过布尔匹配、liveDocs/full-delta 可见性过滤和去重。

02 · 分数 sidecar：独立于 Segment 的不可变表

core.NewBlockMaxScoreTable(ids, scores) 接受按 signed DocID 严格递增的并行数组。它复制输入，按 EntryID 的 DocID 编码顺序重排，然后建块上界与上界树。

结构immutable
  • 1每 64 个已评分 Document 建一个块上界。
  • 2在块上界之上再建二叉上界树。
  • 3连续 key 的查分/定位用 O(1) 偏移；稀疏 key 用二分。
  • 4跳转先检查当前块后缀，再用上界树拒绝整块；有效叶块至多顺序检查 64 个分数。
成本O(D) build
存储
约 16 B / 已评分 Document
上界树
大规模下 < 1 B / Document
构建
O(D)
修改
不改 Segment；原子替换引用
gopublish a score snapshot
// ids 按 signed DocID 严格递增；values 一一对应。
scores, err := core.NewBlockMaxScoreTable(ids, values)
if err != nil {
    return err // 保留已发布的旧分数
}
holder.SetScoreSource(scores)

// 查询只读取进入本次调用时取得的快照。
ranked, err := holder.RetrieveTopK(assignments, 100, nil)
!

不要混用：查询不会把旧分数与新上界拼在一起。周期任务应先完整获取并验证新分数，成功后只调用一次 SetScoreSource；失败时保留旧快照。

03 · 块上界剪枝：用 64 个 Document 换一次判断

阈值来自当前 Top N 堆的根：最低分、同分时最大 signed DocID。上界树给出某段 DocID 区间内可能出现的最高排名；只有“上界仍可能胜出”的块才值得检查。

figure 13block max upper-bound tree

为什么是 64？

每 64 个已评分 Document 建一个块上界，是一个工程折中：块越小，上界越紧、跳转越细，但上界树和元数据越多；块越大，结构越省，但一个低分文档会拖松整块上界，导致更多无效检查。当前实现的有效叶块至多顺序检查 64 个分数。

✓

一个直观概率：假设分数独立均匀、阈值已到 0.999，则 64 个 Document 全部低于阈值的概率约为 0.999^64 ≈ 93.8%，很多块可以整体跳过。但这要求高分文档有机会较早满足布尔条件；若高分文档大多不匹配，它们就不能进入堆、抬高阈值。

执行顺序

布尔 pivot

求现有 K-group merge 的布尔 pivot，即第 max(K,1) 个 FieldCursor 的头部 Conjunction。

未满 N：正常匹配，不建堆

继续追加有效结果，不维护堆、不查询分数上界树；首次收满 N 时统一建堆。

已满 N：查上界，找下一个可能胜出的 DocID

以堆根为阈值，在同一分数快照中寻找 pivot 之后下一个可能胜出的位置。

推进全部游标，继续布尔匹配

包括 Exclude 与 wildcard。跳过的一段同时被布尔与分数条件证明无用。

04 · 延迟建堆：先追加，满 N 再整理

结果数组未满 N 时只追加；首次达到 N 个不同有效结果时，自底向上统一建堆。之后只保留 N 个赢家，用堆替换维护。这样把“前 N 个逐个维护堆”的最坏 O(N log N) 调整，改为追加加一次 O(N) 建堆。

figure 14append → heapify → replace
容量策略没有改变O(N) memory

构造器仍按请求 N 预分配结果数组和固定容量去重表。请求 Top 1,000,000、实际只命中 1,000 时，虽然不会建堆，预分配与 Reset 的清空成本仍可能明显。

复用仍会清空Reset O(N)

复用 collector 前必须 Reset，它会清空整个去重表。关闭分数剪枝也不会消除这些容量成本。

05 · 缺失分数、可见性与复用

sidecar 可以比索引缺少或多出 DocID。默认把缺失分数视为 0；也可以选择直接排除缺分文档。两种策略对“阈值能否剪枝”有不同影响。

MissingScoreZero · 默认zero

缺分文档按 0 分竞争。阈值不高于 0 时，无法从稀疏 sidecar 枚举所有缺失 ID，区间剪枝保守停用；这保证负分、缺分、零分平局都不漏结果。阈值高于 0 时缺失文档无法胜出，可以安全剪枝。

MissingScoreSkipskip

缺分文档不进入结果，可能返回不足 N 个。通过可复用 collector 选择：SetMissingScoreMode(core.MissingScoreSkip)。

Composite 的共享堆

full 和各 delta 流式写入同一个 collector。累计满 N 后统一建堆，后续层共享已经抬高的阈值。full 的 ChangedDocs、delta 的 DeletedDocs 和各 engine 的 liveDocs 在加入 collector 之前生效；旧版本或删除文档不会抬高阈值。

Result = (FullResult − ChangedDocs) ∪ (可见 DeltaResults − DeletedDocs)
!

为什么 scored collector 收满 N 后不能返回 CollectStop？因为 EntryID 不是分数顺序，后面的 Document 仍可能分数更高。只有可靠上界允许提前结束。

复用示例

goper-worker TopK collector
collector := core.NewTopKCollector(100, scores.Snapshot())
collector.SetMissingScoreMode(core.MissingScoreSkip)

// 每次新查询重置，整次查询固定这个 snapshot。
collector.Reset(scores.Snapshot())
err := holder.RetrieveWithCollector(assignments, collector)
ranked := collector.Scored() // 独立拥有的排序结果

构造后复用时，Add、去重、统一建堆、堆替换和上界查询不分配内存；完整查询的编码、PostingIterator 初始化和最终结果复制仍有原有分配。

07 · 路径选择：没有一种策略覆盖全部分布

路径最有利场景代价 / 边界状态
布尔 pivot + sidecar 区间上界宽查询、小 N、能较早形成高阈值单次查询固定分数；前缀边界、缺分保守处理已实现
普通布尔跳转 + 有界堆极窄查询；高分沿 EntryID 一直递增枚举全部布尔命中；不会因收满 N 提前停止已实现，可关闭剪枝
全局分数顺序 + forward matcher分数与查询无关，命中率高，N 很小需要可随机访问的前向求值器；验证 N 个命中即可停止下一阶段验证
按上界优先访问 DocID 块高分集中在 EntryID 后半部或少数块需要可按块乱序 seek 的游标；随机 mmap 访问成本设计候选
每 shard/layer 独立 Top N 再合并多核 / 分布式检索每层先做可见性过滤和去重；动态阈值只能由真实赢家形成当前为串行共享堆
→

可关闭：对命中极少或上界不易剪枝的查询，传 be_indexer.WithScorePruning(false) 使用普通布尔跳转，结果仍是精确 Top K。
