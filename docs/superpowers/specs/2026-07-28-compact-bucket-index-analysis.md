# CompactBucketIndex vs RangeIndex: 性能分析

## 1. 架构概述

### RangeIndex (Segment Tree)
- **空间**: O(n log m)，n = 区间数，m = 唯一端点数
- **查询**: O(log m + K)，K = 命中数
- **构建**: O(n log m)

### CompactBucketIndex
- **空间**: O(n + m)，n = 区间数，m = 桶数
- **查询**: O(1) + K，K = 命中数
- **构建**: O(n log n + n × b)，b = 平均覆盖桶数

## 2. 性能对比 (Intel i7-9750H, Go 1.25)

### 2.1 均匀分布

| 区间数 | RangeIndex (ns/op) | CompactBucket (ns/op) | 加速比 |
|--------|-------------------|----------------------|--------|
| 1,000 | 136.6 | 49.4 | 2.8x |
| 10,000 | 333.6 | 80.1 | 4.2x |
| 100,000 | 1,245 | 132 | 9.4x |

**结论**: 均匀分布下 CompactBucket 显著优于 RangeIndex，且优势随规模增大而扩大。

### 2.2 偏斜分布 (80% 数据集中在 1% 范围)

| 区间数 | RangeIndex (ns/op) | CompactBucket (ns/op) | 加速比 |
|--------|-------------------|----------------------|--------|
| 1,000 | 136.6 | 132 | 1.0x |
| 10,000 | 333.6 | 351 | 0.95x |
| 100,000 | 1,245 | 3,136 | 0.4x |

**结论**: 偏斜分布下 CompactBucket 性能退化，热点桶内区间过多导致扫描开销增大。

### 2.3 聚类分布 (10 个聚类中心)

| 区间数 | RangeIndex (ns/op) | CompactBucket (ns/op) | 加速比 |
|--------|-------------------|----------------------|--------|
| 1,000 | 136.6 | 114 | 1.2x |
| 10,000 | 333.6 | 729 | 0.46x |
| 100,000 | 1,245 | 2,144 | 0.58x |

**结论**: 聚类分布下 CompactBucket 性能退化，多个聚类可能导致热点桶。

## 3. 内存使用对比

| 区间数 | RangeIndex (bytes) | CompactBucket (bytes) | 压缩比 |
|--------|-------------------|----------------------|--------|
| 1,000 | 222,600 | 105,192 | 0.47x |
| 10,000 | 2,247,968 | 489,320 | 0.22x |
| 100,000 | 21,342,408 | 4,323,696 | 0.20x |

**结论**: CompactBucket 内存使用显著低于 RangeIndex，尤其在大规模数据下优势明显。

## 4. 谓词支持

### 4.1 谓词到区间映射

| 谓词 | 区间映射 | 示例 |
|------|---------|------|
| `age = 25` | [25, 25] | 单点区间 |
| `age in [18, 25]` | [18, 18], [25, 25] | 多个单点区间 |
| `age > 18` | [19, MaxInt64] | 无限区间 |
| `age < 60` | [MinInt64, 59] | 无限区间 |
| `age between [18, 60]` | [18, 60] | 闭区间 |

### 4.2 查询逻辑

```go
// 等值查询
age = 25  →  Query(field, 25)

// 范围查询
age > 18  →  Query(field, 19..MaxInt64)  // 需要特殊处理无限区间
age < 60  →  Query(field, MinInt64..59)
age between [18, 60]  →  Query(field, 18..60)
```

## 5. 适用场景分析

### 5.1 适合 CompactBucketIndex 的场景

1. **均匀分布数据**: 性能提升 3-9 倍
2. **大规模数据**: 内存节省 80%
3. **高频查询**: 零分配设计减少 GC 压力
4. **mmap 存储**: 序列化格式友好

### 5.2 适合 RangeIndex 的场景

1. **偏斜分布数据**: 避免热点桶退化
2. **聚类分布数据**: Segment Tree 的对数复杂度更稳定
3. **小规模数据**: 两者性能差异不大

### 5.3 混合策略

对于实际业务场景，建议采用**混合策略**：

1. **数据分布检测**: 构建时统计区间分布
2. **动态选择**: 根据分布特征选择最优索引类型
3. **自适应桶大小**: 对偏斜数据使用更大的桶

## 6. 性能退化分析

### 6.1 CompactBucketIndex 退化条件

| 退化条件 | 影响 | 缓解措施 |
|---------|------|---------|
| 热点桶区间过多 | 查询退化为 O(K) | 动态调整桶大小 |
| 区间长度差异大 | 大区间覆盖过多桶 | 分层桶结构 |
| 查询点集中在热点桶 | 缓存失效 | 预热或缓存 |

### 6.2 RangeIndex 退化条件

| 退化条件 | 影响 | 缓解措施 |
|---------|------|---------|
| 区间高度重叠 | 节点 PostingList 过长 | 分割重叠区间 |
| 端点分布不均 | 树不平衡 | 自适应分割点 |

## 7. 建议

### 7.1 短期优化

1. **保留 RangeIndex 作为默认**: 稳定性优先
2. **提供 CompactBucketIndex 选项**: 用于已知均匀分布场景
3. **添加分布检测**: 自动选择最优索引

### 7.2 中期优化

1. **自适应桶大小**: 根据数据分布动态调整
2. **分层桶结构**: 处理偏斜分布
3. **并行构建**: 加速索引构建

### 7.3 长期优化

1. **机器学习预测**: 预测查询模式，优化索引结构
2. **混合索引**: 结合 Segment Tree 和 Bucket 的优势
3. **分布式索引**: 支持超大规模数据
