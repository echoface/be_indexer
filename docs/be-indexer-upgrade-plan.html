1. 摘要与目标

BE Indexer 是一个 Go 实现的布尔表达式匹配索引核心库，负责根据输入特征快速找出满足 AND、OR、NOT、范围和模式匹配条件的规则或文档。

升级目标是将它演进为高性能、低内存、可观测、可版本化、可分段和可分片部署的检索内核，而不是扩展为广告、竞价、计费、排序或其它业务引擎。

核心路线：先建立 Snapshot 和 immutable index 基础，再进行压缩存储和查询规划，最后扩展增量 Segment、Compaction 与分片协调。

更省内存

TermID、连续内存布局、自适应 Posting 编码和 immutable Segment。

更快查询

基数统计、选择性估算、Cursor/Bitmap 自适应和 Segment 短路。

稳定发布

Build、Validate、Publish、Rollback 和 Manifest 原子切换。

生产可运营

Metrics、Tracing、Explain、Inspector、限流和故障恢复。

2. 当前实现评估

2.1 已有能力

  • 基于论文的 K-Groups / Boolean Expression Index 实现。
  • roaringidx/ 位图索引实现。
  • 默认倒排表、数值范围索引和 Aho-Corasick 容器。
  • CompactBEIndex 紧凑索引实现。
  • 文档级增量构建缓存和 Schema Hash。
  • Result Collector、Posting Cursor 和基础 Dump 能力。

2.2 主要不足

领域当前状态升级方向
存储大量使用 Go Map、字符串和可变 Slice。Dictionary、TermID 和连续 Posting 存储。
查询主要依赖游标初始化、排序和固定扫描流程。统计信息、代价模型和 Query Plan。
生命周期偏向一次构建后查询。immutable Segment 和 Snapshot Reader。
事务版本已有构建过程测试，不是完整持久化事务。Manifest、原子发布、回滚和恢复。
观测主要依赖日志和 Dump。Metrics、Tracing、Explain 和 Inspector。
测试注意：核心包测试可以通过，但全量 go test ./... 会受到 example/compare_benchmark 中外部私有依赖的影响。建议后续通过 build tag 或独立模块隔离该示例。

3. 总体设计原则

  1. 查询与构建分离：查询只读取 immutable index，构建使用独立 Builder。
  2. Segment 不可变：发布后不原地修改，便于并发读、快照、持久化和回收。
  3. Manifest 管理版本：查询读取 Snapshot，不直接依赖可变 Index。
  4. 统计驱动：查询计划基于 Posting 基数和选择性，而不是固定规则。
  5. 可观测但不污染热路径：监控和 Debug 可关闭、可采样、低开销。
  6. 职责收敛：核心库只负责索引和检索，不负责竞价、计费、排序和服务治理。
  7. 渐进式演进：先建立基础抽象，再迁移现有实现。

5. 压缩与内存效率

5.1 Dictionary 与 TermID

当前 map[Term]Entries 会带来字符串、Map bucket、Term 复制和 Slice 扩容成本。建议拆成 Field Dictionary、Term Dictionary 和 Posting Store：

field -> fieldID
fieldID + normalized value -> termID
termID -> compressed posting list
type FieldID uint16
type TermID uint32
type PostingID uint32
type DocID uint64

5.2 自适应 Posting 编码

数据特征推荐编码
极短列表内联小数组
稀疏递增 IDDelta + Varint
中等密度Roaring Array Container
高密度Roaring Bitmap Container
连续区间较多Run Container

5.3 连续内存布局

FieldMeta[]
TermMeta[]
PostingOffset[]
PostingBytes

该布局有利于降低 GC 压力、改善 CPU Cache 局部性、支持 mmap，并统计真实内存占用。

6. 查询规划与执行

6.1 查询流水线

Parse -> Normalize -> Estimate -> Plan -> Execute -> Collect
type QueryPlan struct {
    Steps         []PlanStep
    EstimatedCost uint64
    EstimatedHits uint64
    Strategy      PlanStrategy
}

6.2 基于基数的排序

对于 AND 条件，优先执行最稀疏的条件。例如：A 的基数为 10、B 为 1,000,000、C 为 100 时，执行顺序应优先考虑 A、C、B。

规划时还应考虑 Posting 类型、否定条件、Segment 数量、查询缓存和历史执行数据。

6.3 操作策略

操作策略
AND从最小 Posting List 开始做交集，必要时使用 Bitmap。
OR优先合并低基数列表，避免过早物化巨大结果。
NOT有候选集时使用 AndNot；无候选集时使用 live-doc bitmap，并根据选择性延后执行。

6.4 Cursor 与 Bitmap 自适应

  • 低基数、稀疏结果：Sorted Posting / Cursor。
  • 中高基数：Roaring Bitmap。
  • 多 Segment：Segment-level filtering + Merge。
  • 复杂 NOT：Candidate Bitmap + AndNot。

6.5 Explain

type ExplainResult struct {
    SnapshotVersion uint64
    Plan            QueryPlan
    ActualSteps     []StepStats
    TotalDuration   time.Duration
}

7. 分段与分片

7.1 Segment 生命周期

Building -> Sealed -> Validated -> Published -> Retired -> Deleted

Segment 至少包含 Header、Segment ID、Generation、Schema Version、Field Dictionary、Term Dictionary、Posting Index、Posting Data、Live Docs、统计信息和 Checksum。

7.2 Segment 合并

建议先实现只读 Segment 和周期性重建，确认格式和 Snapshot 机制稳定后，再增加增量 Segment 与后台 Compaction。

  • 合并小 Segment。
  • 合并相同 Field/Term 的 Posting。
  • 合并 Tombstone 并重建统计信息。
  • 后台限速，不影响在线查询。

7.3 分片策略

策略优点缺点
DocumentID Hash写入均匀，大小容易控制。查询通常需要广播和去重。
租户、业务线或地域路由范围小，隔离性好。可能出现热点和大小不均。
高选择性维度可以减少广播。维度变化可能造成迁移。

7.4 Shard API

type ShardReader interface {
    Snapshot() Snapshot
    Retrieve(ctx context.Context, query Query, collector Collector) error
}

type ShardRouter interface {
    Route(query Query) []ShardID
}

核心库可以提供轻量 MultiShardReader，负责并发查询、超时、结果合并、去重和部分失败策略；服务发现、配置中心和副本调度留给上层。

8. 监控与稳定运行

8.1 可插拔 Metrics

type Metrics interface {
    Counter(name string, value int64, labels ...Label)
    Histogram(name string, value float64, labels ...Label)
    Gauge(name string, value float64, labels ...Label)
}

8.2 核心指标

  • 查询：总数、错误、超时、P50/P95/P99、结果数、扫描 Segment 数和扫描 Posting 数。
  • 构建：耗时、文档数、失败数、跳过 Conjunction 数、Segment 字节数和压缩比。
  • 内存：Index、Dictionary、Posting、Bitmap、Builder 和查询临时内存。
  • 版本：当前 Snapshot、发布次数、回滚次数、旧版本读者数和恢复次数。

8.3 稳定性保护

  • 查询开始时固定 Snapshot，发布不影响已有查询。
  • 构建失败时线上版本不变，临时产物自动清理。
  • 支持查询超时、最大返回数、最大扫描量和最大临时内存。
  • Compaction 和构建使用有界并发和限速。

9. 事务化与版本化索引管理

9.1 版本概念

版本含义
DocumentVersion业务文档版本。
IndexVersion一次完整索引快照版本。
SchemaVersion字段、解析器、编码和格式版本。
SegmentGeneration某个 Segment 的生成版本。

9.2 Snapshot API

type Snapshot interface {
    Version() uint64
    SchemaVersion() uint64
    Retrieve(query Query, opts ...QueryOption) (Result, error)
    Close()
}

type IndexManager interface {
    Open() error
    Current() Snapshot
    BeginBuild(opts BuildOptions) (IndexWriter, error)
    Publish(build BuildResult) (Snapshot, error)
    Rollback(version uint64) error
    ListVersions() ([]VersionInfo, error)
}

9.3 Build、Validate、Publish

BeginBuild -> Write / Build -> Seal -> Validate -> Commit Manifest -> Publish Snapshot

Validate 至少检查 Schema、Checksum、Posting Offset、Dictionary 排序、EntryID 合法性、Conjunction 限制、统计信息和随机查询抽样结果。

9.4 Manifest 原子发布

manifest.tmp -> fsync -> rename(manifest.current) -> fsync directory

已有查询继续使用旧 Snapshot，新查询使用新 Snapshot。旧版本应在所有读者退出后再回收。

10. 生产性能要求

说明：“Google / Yahoo 级别”必须转化为真实数据、并发、延迟分位数、内存上限和故障场景下的可测量指标。

10.1 必测范围

  • 10 万、100 万、1000 万和 1 亿文档或规则。
  • 每个文档 1、10、100 个 Conjunction。
  • 低基数、高基数、稀疏、多值、范围和 AC 模式字段。
  • 单字段、多字段 AND、OR、NOT、空结果、高命中率和低命中率查询。

10.2 建议初始 SLO

指标目标
P50 查询延迟< 100 μs
P95 查询延迟< 1 ms
P99 查询延迟< 5 ms
查询错误率< 0.01%
发布切换< 100 ms，且查询不失败
查询额外分配目标 0～3 次

11. 线上调试与内存查看

11.1 Debug Inspector

type IndexInspector interface {
    SnapshotInfo(ctx context.Context, version uint64) (SnapshotInfo, error)
    SegmentInfo(ctx context.Context, version uint64) ([]SegmentInfo, error)
    FieldStats(ctx context.Context, version uint64, field FieldID) (FieldStats, error)
    TermStats(ctx context.Context, version uint64, field FieldID, value string) (TermStats, error)
    Explain(ctx context.Context, version uint64, query Query) (ExplainResult, error)
    SamplePosting(ctx context.Context, version uint64, term TermID, limit int) ([]DocID, error)
    MemoryReport(ctx context.Context, version uint64) (MemoryReport, error)
}

11.2 安全约束

  • 输出大小限制、超时、取消和采样。
  • 基于指定 Snapshot 读取，不读取正在构建的可变数据。
  • 不默认导出全部规则或全部文档内容。
  • 支持脱敏 Hook，不阻塞正常查询线程。

12. 核心库边界

12.1 核心库负责

  • 表达式编译、归一化、字段解析和索引编码。
  • Posting / Bitmap 存储、Query Planning 和 Query Execution。
  • Segment、Snapshot、Manifest 和索引校验。
  • Metrics、Tracing 和 Debug Inspector Hook。

12.2 核心库不负责

  • 竞价、计费、广告排序、召回策略和用户画像。
  • RPC、服务发现、配置中心、权限系统和任务调度。
  • 数据同步、分布式选主、节点治理和副本调度。

13. API 演进建议

13.1 保持现有 API 兼容

builder := NewIndexerBuilder()
index := builder.BuildIndex()
result, err := index.Retrieve(assignments)

13.2 新增 Snapshot / Writer API

manager, err := OpenIndexManager(opts...)
build, err := manager.BeginBuild(BuildOptions{SchemaVersion: 8})
if err != nil { return err }
if err := build.AddDocument(doc); err != nil { return err }
artifact, err := build.Seal()
if err != nil { return err }
if err := artifact.Validate(); err != nil { return err }
snapshot, err := manager.Publish(artifact)
result, err := snapshot.Retrieve(ctx, query)

13.3 查询选项

snapshot.Retrieve(ctx, query,
    WithLimit(100),
    WithExplain(),
    WithQueryTimeout(time.Millisecond),
)

14. 分阶段实施计划

Phase 0：基线和契约冻结

  • 固定查询语义和边界条件。
  • 建立随机表达式测试及 K-Groups / Roaring 交叉校验。
  • 建立数据规模、延迟、吞吐和内存基线。
  • 补充并发读、Race 和错误恢复测试。

Phase 1：读写分离与 Snapshot

  • 引入 Snapshot。
  • Builder 生成独立索引。
  • Publish 原子切换，旧 Snapshot 延迟回收。
  • 查询禁止访问正在构建的对象。

Phase 2：Immutable Segment 与压缩存储

  • 实现 Dictionary、TermID 和连续内存布局。
  • 实现自适应 Posting 编码。
  • 定义 Segment 文件格式、Checksum 和 Loader。
  • 实现 Memory Report 和 Debug Inspector。

Phase 3：Query Planner

  • 记录 Posting 基数和 Term 选择性。
  • 实现 AND / OR / NOT 策略选择。
  • 实现 Segment 跳过、Query Plan 和 Explain。
  • 自适应选择 Cursor 或 Bitmap。

Phase 4：增量 Segment、Tombstone 和 Compaction

  • 实现 Delta Segment、Delete / Update 和 Tombstone。
  • 实现后台 Segment Merge、限速和失败恢复。

Phase 5：分片和多节点协调

  • 实现 ShardReader、ShardRouter 和 MultiShardReader。
  • 实现并行查询、超时、取消、结果合并和去重。
  • 定义分片级版本一致性。

15. 验收标准

15.1 正确性

  • 新旧执行器结果一致。
  • AND、OR、NOT、范围、多值和重复字段语义有测试。
  • 随机表达式交叉校验通过。
  • 发布、回滚和恢复不会产生错误版本结果。
  • 构建失败不会污染线上版本。

15.2 性能

  • P50/P95/P99 达到项目 SLO。
  • 压缩后内存相对基线下降。
  • 查询热路径分配和 GC 影响有数据证明。
  • 查询规划能减少 Posting 或 Segment 扫描。
  • Compaction 不导致线上延迟突破 SLO。

15.3 运维

  • Metrics 可查看查询、构建、内存和版本状态。
  • Explain 可以定位慢查询。
  • Inspector 可以查看指定 Snapshot 的 Segment、Term 和内存信息。
  • Debug 操作有大小限制、超时和取消能力。
  • 崩溃后可以恢复到最近一个合法 Manifest。
第一阶段优先事项：Snapshot + Manifest + 原子发布 + 只读查询隔离。这是后续压缩、分段、回滚、分片和稳定运行的共同基础。
