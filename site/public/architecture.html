01 · 读写分离：复杂度留在离线

构建器与查询引擎互不依赖。离线路径可以慢、可以外排、可以反复校验；在线路径只读不可变数据，尽量不分配、不查找、不复制。

figure 02package dependency

构建路径

Document→ Normalize / Validate→ SchemaCodec→ PredicateEncoder→ SegmentBuilder→ Segment v5

构建阶段完成所有昂贵工作：展开 DNF、校验同字段唯一 Include、编码值、外排大字典、压缩 interval、构建 AC 自动机、写 checksum。在线路径不重新解析规则，也不访问原始 Document。

查询路径

Assignments→ EncodeAssignment→ MatchQuery→ FieldCursor × N→ matchConjunctions→ Collector

构造引擎时预解析字段，热路径不重复查 map。每个字段把多值、多 segment 的 posting 游标组合成一个 FieldCursor；所有字段游标在一次查询中串行归并，不自动并行。

i

为什么把 K 放进 ID 而不是单独分桶？因为 K 一旦参与排序，所有相同 K 的 Conjunction 就天然连续。查询无需先决定去哪个桶，也无需为每个 K 维护独立结构；只需在归并时从当前最小 EntryID 读出 K。

02 · 规则模型：DNF、Include 与 K

一个 Document 是一条完整规则；Document 内的 Conjunction 之间是 OR；Conjunction 内的 Predicate 之间是 AND。K 是该 Conjunction 中 Include 约束的数量。

DNF 语义OR of ANDs
Document 1
├── Conjunction A  (K = 2)
│   ├── age ∈ [18, 25]     Include
│   └── city = "beijing"  Include
└── Conjunction B  (K = 0)
    └── city ∉ {"rural"}   Exclude
三个关键语义语义正确优先
  • 1同字段在一个 Conjunction 内最多一个 Include；多个等值放进同一 Constraint，值之间是 OR。
  • 2查询缺少某个 Include 字段时，该 Conjunction 必然不命中。这是 K 的设计，不是漏洞。
  • 3Exclude 只在 Assignment 显式命中被排除值时否决；字段缺失不会触发排除。
!

K = 0 不是“空条件”。只带 Exclude 的 Conjunction 也会产生 wildcard 候选，但命中的 Exclude 仍能否决它；只有真正的空 NewConjunction() 才是无条件规则。

为什么“缺少字段”会直接不命中

倒排索引只为查询实际提供的字段生成游标。一个需要 K 个 Include 的 Conjunction，如果要成立，就必须在 K 个不同字段上各有一个游标命中它。查询没提供字段，就少一个游标，永远凑不齐 K。这不是漏召回，而是 DNF 的 AND 语义在倒排上的自然结果。

03 · EntryID：把 K 放进排序键

EntryID 是一个 64 位整数。它不记录字段或 term 身份，只记录“这个倒排条目属于哪个 Conjunction、是 Include 还是 Exclude”。字段身份来自它所在的 Posting List。

ConjID = reserved(4) | K(8) | index(8) | sign(1) | abs(DocID)(43)
EntryID = ConjID << 4 | include(1bit)  →  K(8) | index(8) | sign(1) | abs(DocID)(43) | reserved(3) | include(1)
交互式位布局EntryID · 64 bit
K · bits 63–56 index · 55–48 sign · 47 abs(DocID) · 46–4 reserved · 3–1 include · 0
63–5655–4847–4039–3231–2423–1615–87–0
EntryID hex decimal ConjID hex

示意输入受 DocID ∈ [-(2^43−1), 2^43−1]、K < 256、Conjunction 数 < 256 约束。ConjID 低 4 位留给 EntryID 的极性位。

排序顺序为什么是这样

EntryID 的字典序等价于：K → Conjunction index → sign → abs(DocID) → Include。这意味着：

  • 同 K 的条目连续。查询可以从最小头部动态读取 K，不需要物理 K 分桶。
  • conjunction 内 Exclude 在 Include 之前。同一 Conjunction 的 Exclude 条目低位为 0，Include 为 1。
  • EntryID 顺序不是 signed DocID 顺序，也不是分数顺序。Top K 不能假设先遇到的 Document 分数更高。
K=0 · wildcard K=1 · doc 10 K=1 · doc 20 K=1 · doc 30 K=2 · doc 5 K=2 · doc 10 K=2 · doc 20 K=3 · doc 8

示意：升序排列后，相同 K 的条目自然聚成一段。K 越高，需要的字段游标越多。

04 · K-Groups：pivot 与单次多路归并

所有字段游标（以及 wildcard 游标）按当前 EntryID 排序。取第 max(K, 1) 个头部作为 pivot。pivot 之前的 Conjunction 不可能凑齐 K 个字段，因此可以整段跳过。

interactivepivot · SkipTo · match

四步循环

排序头部，读取 K

每个 FieldCursor 暴露当前最小 EntryID。按它排序后，从最小头部读出 K，所需字段数 need = max(K, 1)。

取 pivot，判断能否凑齐

第 need 个头部形成 pivot。前 need 个头部若属于同一 ConjID，则该 Conjunction 的所有 Include 字段都命中；否则 pivot 之前的候选缺少足够字段，跳过。

命中则收集，Exclude 则短路

Include 命中后交给 collector；若同一 Conjunction 的 Exclude 先被命中，则否决它，并把仍指向它的游标推进到该 Conjunction 之后。不影响同 Document 的其他 OR 子句。

SkipTo 推进，移除耗尽游标

用 galloping + 二分把游标推到目标 EntryID。排序后用 RemoveExhausted() 移除尾部耗尽游标，直到全部耗尽或 collector 返回 CollectStop。

✓

正确性直觉：pivot 之前的任何 Conjunction，最多只能由前 K−1 个字段游标贡献条目；其余游标已经在 pivot 或更后面，凑不齐 K 个 Include。K 又随 EntryID 不减，所以跨 K-group 也不会漏掉更小的候选。

Galloping SkipTo

SkipTo(target) 把游标移到第一个 EntryID ≥ target 的位置。它先检查当前条目，然后以指数增大的步长探测，找到目标所在的小区间后再二分。顺序推进和偶尔的大跨度跳转都能受益。

N = 100KBinary SearchGallopingSpeedup
Seq (+1)15.1 μs4.1 μs3.7×
Stride 16167 μs58 μs2.9×
Jump 641.73 μs1.66 μs≈ equal

历史合成测量，用于解释机制差异，不是当前性能保证。同一优化同时用于内存 SliceIterator 与 mmap flatPostingCursor；SkipTo 循环本身不分配。

05 · Segment v5：为 mmap 设计的文件

Segment 是一串按 8 字节对齐的 block。所有整数小端序；posting 与 wildcard 块可以在对齐的小端主机上直接借用为 Go slice。

共享的 posting 原语

FlatPostingList = Count(u32 LE) | Pad(u32 = 0) | EntryID × Count (u64 LE)

Pad 的唯一职责是让 EntryID 数组从 8 字节边界开始。Reader 在 little-endian 且地址对齐时直接 unsafe.Slice；其他端序或非对齐输入显式逐项解码，保证正确性。

打开时校验：结构永远检查

始终校验structure
  • ✓magic、版本、metadata 与 block 边界、schema hash
  • ✓FlatDict 长度、偏移顺序与严格词典序
  • ✓posting 引用长度、count 一致性与 padding
  • ✓AC fail 链、output 引用；range 树拓扑、不可达节点与环
checksum 开关payload only

开关只控制是否扫描 payload 哈希，不关闭结构校验。range 验证使用迭代遍历，避免坏树导致递归栈溢出。第三方容器仍负责自己的私有格式。

06 · Wildcard 与零拷贝：把复制和排序消掉

K=0 的 Conjunction 不产生任何 Include 条目，只产生 wildcard。Segment v5 把每段的 wildcard 内嵌为 __wildcards block；读取时借用 mmap，查询时用内部堆做懒 K 路归并。

figure 04zero-copy decision path

Wildcard 的懒归并

朴素做法

  • 每段 wildcard 载入时复制到 heap
  • 所有段合并后再排序一次
  • 3× copy + O(N log N) sort

当前实现

  • 每段 SliceIterator 直接引用 mmap
  • 组合成单个 FieldCursor
  • 内部堆做懒 K 路归并：0 copies + 0 sort

查询初始化时，每段 wildcard 的 SliceIterator 被放进同一个 FieldCursor。它和普通字段游标一起参与归并，不需要 load-time merge。只有实际被消费的条目才会从 mmap 页中缺页载入。

!

内存数字怎么读：404 MB 是 5M docs / ~50M EntryID 的示例 Segment 文件；Reader 常驻约 270 KB，其余是 mmap 虚拟地址。首次查询会触发缺页，RSS 约增长 5 MB；稳态 4–10 MB 取决于热点 posting 页。不要只按文件大小估算 RSS。

07 · full + delta：不可变快照与原子切换

生产推荐一个 full 加一个累计 delta，各自可以包含多个 segment。每轮 delta 覆盖当前 full 截止位置之后的全部变更，发布时替换旧 delta。

Result = (FullResult − ChangedDocs) ∪ (可见 DeltaResults − DeletedDocs)

T2

任何一步失败，关闭已创建的 Engine/Reader，旧快照继续服务。

T3

原子发布新快照

新查询立即使用新快照；在途查询继续持有旧 mmap。

T4

最后一个查询释放旧快照

引用计数归零后 unmap。旧快照的读取失败不会影响当前服务。

08 · 正确性与边界：哪些话不能说

这个项目把“语义正确、数据完整性、线上可用”放在性能之前。因此文档里也明确写了哪些优化只是手段，哪些边界不能外推。

三个常被误读的边界

  • 零拷贝不是零分配。完整 Retrieve 仍会为编码、游标组合和结果所有权分配；核心 SkipTo/归并循环才保持零分配。
  • 增加段数不会自动并行。单次查询串行组合所有段游标；并发查询才能利用多核。
  • 外排不是严格内存上限。它控制部分构建峰值，热点 posting、去重集、最终字典和 range 数据仍占内存。
