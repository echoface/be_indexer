02 · 内存足迹：文件很大，Reader 可以很小

示例负载：5M Documents，每文档 10 个字段，约 50M EntryIDs。关键不是“文件 404 MB 所以进程要 404 MB”，而是 mmap 把文件映射成虚拟地址，真正进入 RSS 的是被访问的页。

组件内存说明
Segment file~404 MB磁盘 / 虚拟地址；mmap 映射，不要求常驻 RSS
SegmentReader (RSS)~270 KBdict + 指针；其余是 mmap 视图
BooleanEngine~2 KBschema codec only
Per-query (hot)~61 KBcursors + collector
First-query RSS growth~5 MBtouch 到的 posting 页被 fault 进 page cache
Steady-state RSS4–10 MB热 posting 页；取决于访问局部性
!

不要只按文件大小估算 RSS。FlatDict 词条元数据、Range 的部分结构、AC 的索引元数据会在打开时解码到 heap；“posting zero-copy”成立，“整个 SegmentReader zero-copy”不成立。真实占用请用压测。

mmap 的收益与代价

收益

  • 大 posting/wildcard 数组无需复制到 heap
  • 冷启动只映射，不读完整文件
  • 页缓存由 OS 管理，可跨进程共享
  • 发布不可变 Segment，天然适合多版本并存

代价

  • 首次访问触发缺页，尾部延迟抖动
  • 文件必须保持不可变；删除/覆盖会破坏视图
  • 回收要等最后一个查询释放引用
  • 随机访问受页缓存命中率影响

03 · Galloping SkipTo：顺序推进是主场景

SkipTo(target) 先把游标移到第一个 EntryID ≥ target 的位置。它先走当前条目快路径，再指数探测，最后二分。顺序推进和偶尔的大跨度跳转都能受益；真正的大跳跃上，二分已经足够好。

每组以自身二分耗时为 100% 归一化。同一优化同时用于内存 SliceIterator（wildcard）与 mmap flatPostingCursor。SkipTo 循环本身不分配；完整 Retrieve 仍允许受控分配。

04 · Wildcard：raw EntryID vs Roaring64

Wildcard（K=0）在内嵌 Segment 时是一段排序 EntryID 数组。可选的 Roaring64 sidecar 用压缩位图表示同一集合，在稠密场景下减少存储和反序列化成本。

N = 100KRaw []EntryIDRoaring64结果
Storage (dense)800 KB200 KB25% · 4× smaller
Load (deserialize)76 μs38 μs2× faster
SkipTo seq scan3.9 ms2.1 ms1.9× faster
i

默认路径不依赖 sidecar。Segment v5 内嵌 __wildcards block；Reader 在对齐的小端主机上借用 mmap，查询时每段 SliceIterator 组合成单个 FieldCursor，内部堆做懒 K 路归并——0 copies、0 sort。Roaring64 是可选存储/加载优化（见 core/wildcard_iter_bench_test.go）。

07 · 延迟建堆：有正收益，也有 +12.5%

固定 M=4096、DenseScoreTable，三次取中位数，单位 μs。包含 Reset、查分、去重与收集；不包含 collector 构造、布尔检索、上界查询和最终 Scored() 的复制排序。

怎么读：N > M 时始终不建堆，三种分布都减少收集耗时；N = M 的随机分数用例反而慢约 12.5%，说明一次性建堆的常数、原先逐项插入的实际调整量也会影响结果。N < M 时，满堆之后的替换工作仍然存在，不能把填充阶段的改善等同于整个查询同比例加速。

所有用例 0 B/op、0 allocs/op，结果先与完整排序对照。请求超大 N 时，构造预分配与 Reset 的 O(N) 清空成本不在本表内。

08 · 构建与冷启动：外排不是内存上限

构建offline
  • 1单段建议 ≤ 5M docs；段数增加会提高串行游标归并成本。
  • 2MaxDistinctKeysInMemory 限制的是 distinct key 数，不是 posting 数；热点 key 仍占内存。
  • 3外排控制部分峰值，不等于严格内存上限；最终字典、range 区间、去重集仍在内存。
  • 4全内存与溢写配置输出相同字节；Write() 成功/失败都会关闭并清理私有临时目录。
冷启动page cache
  • 1MmapVerify 会校验文件大小与整文件 SHA-256，冷启动会扫所有数据页。
  • 2MmapTrustPublished 跳过 payload 哈希，仍保留尺寸、结构、block 边界与 checksum 元数据格式校验。
  • 3首次查询触发缺页，RSS 约 +5 MB；发布后建议预热，避免尾部延迟抖动。
  • 4验证元数据随字典/状态/节点规模增长；关闭哈希不代表常数时间冷启动。

09 · 方法与复现：这些数字是怎么来的

属性read me first
  • ·多数是合成基准或历史测量，不是线上 SLA。
  • ·机器、单轮时间和数据分布都会影响结果；Top K 的 matches/op 是 Conjunction 匹配回调，不是全部 merge 迭代或 SkipTo 次数。
  • ·FST 数字来自参考机，命中路径的分配与 vellum/pool 行为相关，只作相对参考。
  • ·内存表是 5M docs / 10 fields / ~50M EntryIDs 的示例，不是所有负载的承诺。
复现命令Go 1.24+
bash
make test
make build
go vet ./...

go test -race ./core ./engine ./loader

go test ./engine -run '^$' \
  -bench '^BenchmarkTopK$' \
  -benchmem -benchtime=200ms

go test ./core -run '^$' \
  -bench '^BenchmarkTopKFill$' \
  -benchmem -benchtime=200ms -count=3
!

部署选择：以实际业务数据的分布、分位延迟、峰值 RSS、冷启动预算和 sidecar 更新成本为准。不要把一个宽查询随机分数的 321× 外推到全部流量。
