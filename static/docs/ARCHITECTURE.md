## 整体架构

当前 `be_indexer` 采取了严格的**读写分离**和**基于 mmap 的零拷贝**架构。

### 组件概览

```text
┌─────────────────────────────────────────────────────────┐
│                     应用层 (Application)                   │
├─────────────────────────────────────────────────────────┤
│  Document (业务规则)  <====>  Assignments (业务特征)        │
├─────────────────────────────────────────────────────────┤
│                  编译层 (Builder Layer)                     │
│  ┌──────────────────────────────────────────────────┐   │
│  │ BuildSegmentFromDocs() 把 Document 编译为二进制段   │   │
│  └──────────────────────────────────────────────────┘   │
├─────────────────────────────────────────────────────────┤
│                  物理层 (Segment Layer)                    │
│  ┌──────────────┐  ┌──────────────┐  ┌──────────────┐   │
│  │   Builder    │  │ MmapReader   │  │ FlatDict/AC  │   │
│  └──────────────┘  └──────────────┘  └──────────────┘   │
├─────────────────────────────────────────────────────────┤
│                  执行层 (Engine Layer)                     │
│  ┌──────────────┐  ┌──────────────┐  ┌──────────────┐   │
│  │ BooleanEngine│  │  retrieveK   │  │ ResultCollect│   │
│  └──────────────┘  └──────────────┘  └──────────────┘   │
└─────────────────────────────────────────────────────────┘
```

### 数据流

#### 1. 离线编译流程 (Write Path)
```text
1. 接收 []*Document 列表
   ↓
2. 解析并展开 DNF 范式，分配全域唯一的 ConjID
   ↓
3. 对每个 Predicate 的 Value 进行 Tokenize 提取特征串
   ↓
4. 按包含条件数 (K值) 对 EntryID 进行分组隔离
   ↓
5. 彻底排序倒排链，并将数据对齐写入段文件 (.seg)
   ↓
6. 生成 FlatDict 字典块或 AC 自动机块，最后写入尾部元数据
```

#### 2. 在线检索流程 (Read Path)
```text
1. 通过操作系统 syscall.Mmap 挂载 .seg 文件
   ↓
2. 解析尾部 MetaBlock，懒加载字段的 MmapReader
   ↓
3. 接收在线查询 Assignments
   ↓
4. K-Groups 倒序遍历 (从 MaxK 到 1)
   ↓
5. 根据特征串从 FlatDict/AC 获取底层字节流游标 (FieldCursor)
   ↓
6. 执行基于 ConjID 的短路求交与排异算法 (retrieveK)
   ↓
7. 收集命中结果并应用 LiveDocs 过滤
```

## 核心算法

### DNF (Disjunctive Normal Form)
`be_indexer` 基于 DNF 布尔表达式：
```text
(DNF) = C1 OR C2 OR C3 OR ...
其中 Ci = E1 AND E2 AND E3 AND ...
```

### 极简且硬核的 EntryID 编码

为了在多路游标合并时实现极速的维度判断，`ConjID` 和 `EntryID` 被高度压缩在了一个 64 位的整数中：

```text
ConjID (64bit):
[ reserved(4) | size/K(8) | index(8) | negSign(1) | docID(43) ]

EntryID (64bit):
[ -- ConjID(60) -- | empty(3) | incl/excl(1) ]
```
通过比较两个游标当前的 `ConjID` 是否相等，引擎能瞬间判断这两个特征是否满足了同一个文档的同一个子句。

### retrieveK 多路求交与 Z-Entry 短路

核心的检索逻辑 `retrieveK` 利用了数据的完美有序性：
1. 将所有匹配到当前查询的底层游标按 `EntryID` 排序。
2. 提取前 `K` 个游标（因为当前组的子句需要满足至少 K 个包含条件）。
3. 检查 `fCursors[0].ConjID == fCursors[K-1].ConjID`：
   - **如果相等**，说明同一子句同时命中了 K 个包含条件。
   - **检查 `incl/excl` 位**：
     - 如果是 Include（正常情况），则将 DocID 加入命中集合。
     - **如果是 Exclude（排异命中）**，说明触发了 `NOT IN` 条件。当前子句即刻作废，所有游标直接 `SkipTo` 该 ConjID 的下一个元素。**这种短路操作将排除条件从性能负担转化为了加速剪枝的利器。**
4. 推进所有游标，重复循环。

## 物理布局与序列化

为了实现 `mmap` 的零拷贝（Zero-Copy），数据在段文件中的布局被设计为严密的块状结构，完全抛弃了 Go 堆内存对象。

```text
+-------------------------------------------------+
| Magic Number (8 bytes, "BEIDX\0\0\1")           |
+-------------------------------------------------+
| Block 1: Flat Posting Lists (K=1, Field A)      |
| [ EntryID 1 | EntryID 2 | EntryID 3 | ... ]     |
+-------------------------------------------------+
| Block 2: Flat Dict / ACMatcher (K=1, Field A)   |
| [ Term 1 | Offset 1 | Term 2 | Offset 2 ... ]   |
+-------------------------------------------------+
| ... 其他 K 组和字段的数据块 ...                      |
+-------------------------------------------------+
| Segment Metadata Block (JSON)                   |
| 记录每个 Block 的 Type, Offset, Size                |
+-------------------------------------------------+
| Meta Length (8 bytes, uint64)                   |
+-------------------------------------------------+
```
查询时仅读取最后 8 字节拿到元数据，之后所有的倒排链和自动机读取都变成了直接在底层切片上的寻址操作。

## 高级容器机制

由于无法在 `mmap` 后反序列化出复杂的 Go 对象，引擎内置了专门适配物理层的容器：

### 1. FlatDict (扁平字典)
代替了原有的 HashMap。它将变长的字符串和对应的偏移量连续紧凑地拼装在一块内存中。查询时，通过在原生切片上的二分查找定位 Term 并提取其对应的倒排链 Offset。

### 2. AC Automaton (Double-Array Trie)
对于多模式匹配（多关键词检索），传统的 `cedar` 树结构被完全扁平化为 **双数组 Trie (DAT)**。
在构建阶段，生成完整的状态跳转数组 `base` 和 `check`，并直接输出到文件中。
在检索阶段，这块内存被直接转换为 `[]uint32` 的描述符，引擎基于连续数组索引完成 O(1) 的状态跳转，实现了在 mmap 上飞驰的字符串搜索。
